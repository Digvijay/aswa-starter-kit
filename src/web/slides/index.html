Section 1

What a customer needs

People and skills

  • Frontend: HTML, CSS, JavaScript and one SPA framework (React, Vue, Svelte, Blazor)
  • Backend: Azure Functions in Node, Python or .NET 10
  • Cloud fundamentals: resource groups, RBAC, managed identity, basic Bicep
  • Source control: Git, GitHub, GitHub Actions
  • Command-line familiarity: az, azd, func, swa

Azure access

  • An Azure subscription
  • Roles on the target resource group:
    • Contributor — to create resources
    • User Access Administrator — to assign RBAC roles
    • or Owner
  • Quota in the target region for Static Web Apps Standard and Functions Flex Consumption (FC1)
  • Tenant policy that permits user-assigned managed identity

GitHub access

  • A repository (public or private). Standard SKU is required for preview environments on private repos.
  • GitHub Actions enabled on the repository
  • Permission to create an Entra application and federated credential (used by azd pipeline config)

Workstation tooling

Section 2

Building a Static Web App by hand

High-level flow

  1. Write the frontend
  2. Write the API as Azure Functions
  3. Create the resources in the portal or with the CLI
  4. Wire up GitHub Actions for deployment
  5. Add observability, identity and a database after the fact

Step by step


# 1. Resource group
az group create -n rg-myapp -l westeurope

# 2. Scaffold the apps
npm create vite@latest web -- --template react
func init api --javascript

# 3. Create the Static Web App linked to GitHub
az staticwebapp create \
  -n stapp-myapp -g rg-myapp -l westeurope \
  --source https://github.com/me/myapp --branch main \
  --app-location web --api-location api \
  --login-with-github

What is still missing

  • Application Insights and Log Analytics are not wired
  • No database
  • API uses connection strings or keys
  • No Bicep, so the second environment is hand-built again
  • Polyglot support requires a rewrite

Production work begins where most tutorials end.

Section 3

Walkthrough of the starter kit

Three commands


azd init -t Digvijay/aswa-starter-kit
azd env set BACKEND_LANGUAGE python   # or node | dotnet
azd up

You get the Static Web App, the Function App, Cosmos DB, Application Insights, the Log Analytics workspace, the managed identity and the RBAC assignments.

Bicep is built on AVM


module swa 'br/public:avm/res/web/static-site:0.9.4' = {
  params: {
    name: 'stapp-${resourceToken}'
    sku: staticWebAppSku           // Standard by default
    location: staticWebAppLocation // SWA-supported region
    linkedBackend: {
      resourceId: functionApp.outputs.resourceId
      location: location
    }
  }
}

Tags, telemetry, RBAC and diagnostics come from the module — there is no hand-written Microsoft.Web/staticSites block.

Identity flow to Cosmos DB


// User-assigned MI is created up front so its principalId is
// known before the Function App and the Cosmos role assignment.
module cosmosDataRbac 'app/db-rbac.bicep' = {
  params: {
    cosmosAccountName: db.outputs.name
    principalId: uami.outputs.principalId
  }
}
          

const client = new CosmosClient({
  endpoint: process.env.COSMOS_ENDPOINT,
  aadCredentials: new DefaultAzureCredential()
});

Cosmos has local auth disabled. The same code path works locally with az login and in Azure with the user-assigned managed identity (selected via AZURE_CLIENT_ID).

Polyglot toggle


# azure.yaml — one azd service (the SWA), one postdeploy hook
services:
  web:
    project: ./src/web
    host: staticwebapp
hooks:
  postdeploy:
    posix:   { shell: sh,   run: ./scripts/deploy-api.sh }
    windows: { shell: pwsh, run: ./scripts/deploy-api.ps1 }

The hook calls scripts/build-api.{sh,ps1}, which inspects BACKEND_LANGUAGE and stages the chosen runtime into src/api/, then uploads via az functionapp deployment source config-zip --build-remote false.

One azure.yaml. One Bicep tree. Three production-ready runtimes — node, python or dotnet.

CI/CD without secrets


azd pipeline config
  • Creates an Entra application and federated credential for the repository
  • Writes the GitHub Actions workflow
  • Sets the OIDC variables (AZURE_CLIENT_ID, AZURE_TENANT_ID, …)
  • Pull requests get a Static Web Apps preview environment automatically

Day-one observability


azd monitor --overview     # opens Application Insights in the portal
azd monitor --live         # tails live metrics

Because Bicep wired Application Insights into both the Static Web App and the Function App, traces, requests and exceptions are correlated by default.
